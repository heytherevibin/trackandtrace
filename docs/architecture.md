# Architecture

## Layers

```
Browser
  components (src/components/*)            — the visual world; no fetch logic
  stores (src/services/stores/*)           — device state: watchlist, recent, share, install, merge
  api-client (src/services/api-client.ts)  — validated fetch; malformed bodies become errors
Next.js server
  pages (src/app/(site)/*)                 — every traveller page under the site's root layout; unmatched addresses get src/app/global-not-found.tsx (the site's not-found page, server-rendered, 404; sign in on the console host)
  route handlers (src/app/api/*)           — thin: guard → validate → repository/query → jsonOk/jsonError
  pnr-query (src/services/pnr-query.ts)    — the one PNR path: validate → rate limit (IPv6 per /64) → cache → daily live-request budget → single-flight → source
  shared-store (src/services/shared-store.ts) — Upstash Redis (Mumbai) on deployments: shared limits + the encrypted 60 s PNR cache
  sources (src/services/sources/*)         — registry: live seam (unavailable until a provider lands) | railkit | rapidapi (third-party, shown as Trakline; optional fallback between them) | fixture (dev only)
  guarded (src/services/sources/guarded.ts) — each caller of a provider behind its own breaker, one safe retry (network, 502/503/504) and a daily usage count. Generic in question and answer, so it wraps the availability seam too
  watchlist-repo (src/services/watchlist-repo.ts) — supabase-js over RLS-guarded tables
  session (src/services/session.ts)        — verified JWT claims → SessionUser DTO
  proxy (src/proxy.ts)                     — one app, two hosts: the console host (admin.trakline.in; admin.localhost locally) is rewritten into src/app/console with a per-request nonce CSP; elsewhere /console answers 404 and Supabase sessions are refreshed on page requests (skips /api and /monitoring)
  console (src/console/*, src/app/console/*) — the team console: its own root layout, copy and components; only the console tree and the host router (src/proxy.ts, src/app/global-not-found.tsx) import it (tests/unit/console/boundary.contract.test.ts)
  console frame (src/console/components/console-frame.tsx) — every signed-in page's shell: an environment strip, ConsoleMasthead (clock, MemberMenu), the module rail (ConsoleRail on sm and up, ConsoleRailDrawer's left drawer below it — both always mounted, CSS picks one), then the page. `railFor()` (src/console/nav.ts) hides a module until its own `built` flag flips true in the PR that ships its page, so a role with no built module sees no rail and no drawer trigger at all rather than fourteen dead links. 2d-2 flips the first one: 13 Team, which is Owner-only; 2d-2b flips 14 Audit log, which is Owner **and** Admin, so an Admin has a rail — one Record group — for the first time, and Support and Viewer still get none (Overview follows in 2f). `/` redirects to `/keys` — My keys (src/app/console/keys/page.tsx): the Keys plate (list, add, rename, remove), the Profile plate, and the Sessions plate (this device, sign out others), fed by one `console_my_keys` call plus `console_my_sessions`. `/team` (src/app/console/team/page.tsx) is the first numbered module: the Members, Pending invites and Roles plates from one `console_team` call, with the row and invite actions below; a non-Owner is answered with the sheet's own no-access state inside the frame rather than a redirect, and `console_team()` re-checks the role itself regardless. Operating it — the deliberate refusals, and the two situations it cannot answer — is docs/runbooks/console-team.md.
  console audit read (src/app/console/audit-log/page.tsx, src/console/audit/*) — module 14, and the console's only read-only module. The server page runs `requireConsoleMember` with no role floor (as /team does, so a refused role still renders inside the frame), parses the address into `AuditFilters` (src/console/audit/filters.ts — one pure model shared by the page, the GET route and both filter bars; half-open IST day bounds, `null` for no filter), then reads one page of rows (`console_audit`, 50 at a time, clamped to 200) and the Member picker's roster (`console_audit_actors`, the whole log, `distinct on (actor_id)`) in parallel, each falling back to a drawn state rather than throwing. `EntriesPlate` re-reads every later filter change and page turn from `GET /api/audit` (src/app/console/api/audit), and puts the filters in the address with `history.replaceState` — so a filtered view is linkable without a server render. One entry in full comes from `console_audit_entry`, which resolves the key's name through a LEFT join at read time; the export comes from `console_audit_export`, which spends a per-action tap and writes its own row in the same transaction as the CSV it returns. **Reading the log is itself audited**: the server page writes one `Opened the audit log` row per render from `after()` (Done, or Refused for a role below Admin) and none of the read paths above write anything, which is also why no console link may set `prefetch` (tests/unit/console/audit/prefetch-guard.test.tsx). Operating it — the results, the export's limits, and why the environment filter is a convenience and not a boundary — is docs/runbooks/console-audit-log.md.
  console auth (src/console/auth/*, src/console/keys/*) — two Supabase cookies, one project: the console's own `sb-console-auth-token` (src/console/auth/db.ts) is host-only, so trakline.in's traveller cookie never reaches admin.trakline.in and a console session never reaches trakline.in. `requireLinkSession` (src/console/keys/ceremony.ts) gates the key step before a session is key-verified; `requireConsoleMember` (src/console/auth/guard.ts, backed by `console_me`) is the one gate every signed-in console page and route handler runs afterwards. WebAuthn itself — registration and assertion, RP ID scoped to the console host, origin checked exactly — lives in src/console/keys/webauthn.ts behind ceremony.ts's challenge mint/spend pair; nothing else calls `@simplewebauthn/server` for a real ceremony.
  console per-action tap (src/console/components/confirm-its-you.tsx, src/console/keys/tap.ts + tap-client.ts) — a second WebAuthn tap in front of a risky action (removing a key, later: pausing checks, rotating a provider key), form TC-01: `ConfirmItsYou` collects a reason (10–200 characters) and, on submit, mints a challenge (`/api/tap/options`) bound to four fields — action, target, value, reason — hashed one at a time into `console.action_digest` and stored with the challenge. The WebAuthn assertion that follows (`/api/tap/verify`) only proves a real key answered; it touches the key's counter but never spends the challenge. The tap is spent in the database, not the server, inside the same transaction as the action it approves and that action's own audit row (e.g. `console_remove_key`, supabase/migrations/20260921100000_console_my_keys.sql): the mutating function re-derives all four fields itself — the remaining key count from a fresh `count(*)` over the member's own rows, never the client's `value` — and calls `console.use_tap()`, which re-hashes them the same way and looks for an unspent challenge whose digest matches. Any disagreement between what the client minted the tap for and what the database is about to do — a stale count from a second tab, a client bug — surfaces as "no tap for this action" and the action does not run; tests/e2e/console-auth/my-keys.spec.ts drives this through a real ceremony rather than trusting the two sides to agree. Team adds five more tap-gated actions over five different `target`/`value` pairs — an invite (the lower-cased address, the role), a role change (the member's id, the new role), a key reset (the member's id, the key **count** as text), a removal (the member's id, the role they hold today) and a revocation (the invite's id, its address) — each its own way for the mint and the re-digest to part company; tests/e2e/console-auth/team.spec.ts drives all five through real ceremonies, and a bypass that mints a challenge and calls the action with no assertion in between.
  availability crawler (scripts/crawl-availability.mjs, crawl-plan.mjs, crawl-window.mjs, observations-coverage.mjs, observations-report.mjs) — run by a human, never scheduled: one ask per combo per run, a four-day window rolling over a sixty-day horizon, writing `availability_observations` through src/services/observations.ts. Everything but the runner is pure and unit-tested; `npm run source:report` reads the store back and exits non-zero when coverage falls below its threshold, because a past journey date answers 400 and a day nobody crawled is a hole nothing can fill. Operating it — what counts as a gap, why the per-run ceiling is not a per-day one, and what the cursor file is — is docs/runbooks/availability-crawler.md
  telemetry (src/instrumentation*.ts, src/services/telemetry/*) — Sentry on server, edge and browser via the /monitoring tunnel; every event scrubbed of PNRs, emails, tokens, cookies, bodies, queries and URL fragments; off without a DSN
Supabase
  auth.users + public.watchlist_entries (supabase/migrations/*) — RLS: owner-only
  console schema (supabase/migrations/202609200*.sql, 202609211*.sql, 202609221*.sql) — the console's own tables, reached only through security-definer public.console_* functions; the audit log is append-only and console.purge_audit() drops rows past two years. The team's own set — console_team, console_invite_member, console_change_role, console_reset_keys, console_remove_member, console_resend_invite, console_revoke_invite — each does its whole job in one transaction: the change, the member's session revocation, the tap it spends and its audit row, so a caller can never leave half of one behind. The audit log's own readers — console_audit, console_audit_entry, console_audit_actors, console_audit_export — are the only console functions that read it back: all four take a role floor of Admin, every parameter is text/uuid/timestamptz/integer/jsonb (never an enum), and only the export writes anything
```

PNRs never travel in an address, because request paths and query strings are recorded in platform request logs. The result page is `/pnr#<pnr>`: a static shell whose client body (`PnrHashResult`) reads the PNR from the hash and asks `POST /api/pnr` with `{ pnr, fresh? }` in the body. Links are built only by `pnrHref()`. The pre-hydration form posts to `/check` (303 to the hash form), old `/pnr/<pnr>` links answer 308, and `tests/unit/privacy/no-pnr-in-urls.test.ts` fails the build if code puts a PNR in a path or query string again.

## Real-only enforcement points

1. `src/services/env.ts` — `PNR_SOURCE=fixture` refuses to boot in production.
2. `src/services/sources/index.ts` — the registry refuses the fixture again at call time.
3. `snapshot.source` — `"live" | "railkit" | "rapidapi" | "fixture"` on the server only. `toPublicResult()` maps providers to `"live"` before a record leaves `POST /api/pnr`, and the wire schema accepts only `"live" | "fixture"`, so a missed mapping fails closed in the browser. Fixture results render a visible "Sample data" badge; real results read "from Trakline". Adapter messages are neutral (`messages.source.outcomes`). `tests/unit/privacy/no-provider-names.test.ts` fails the build if a provider name appears in pages, components, messages, the wire schema, `public/` or email templates.
3a. `src/services/sources/rapidapi-parse.ts` — the RapidAPI adapter validates every rendered field, never reads the provider's predictions or passenger names, leaves unsent fields unset ("Not returned"), and fails closed on anything unreadable. `RAPIDAPI_KEY` is server-only and required by the env schema when `PNR_SOURCE=rapidapi`.
3b. `src/services/sources/railkit.ts` + `railkit-parse.ts` — RailKit over REST (never its obfuscated SDK), with the same rules; the fare and booking time are never read. `RAILKIT_API_KEY` must look like a RailKit key or production refuses to boot. Both adapters share `irctc-record.ts` for IRCTC seat notation and dates.
3c. `src/services/sources/fallback.ts` — `PNR_FALLBACK` asks a second third-party source only when the first is unavailable, never on "no record"; each answer keeps its own source label, and when both fail the primary's explanation is kept.
4. `public/sw.js` — never caches `/api/*` or `/auth/*`; a stale record can never be served as live.
5. `src/services/log.ts` — every log line is redacted; ten-digit runs never reach the console.
6. Prediction fields exist in the type layer but no component renders them.

## Failure modes (each has an automated assertion)

| Condition | Behaviour |
| --- | --- |
| Source unavailable | UnavailableState with Response / Provenance / Fallback cells; retry |
| Source answered, no record | "No record for this PNR", not an error |
| Rate limited (20/min per address; IPv6 per /64 network, which one client controls) | 429 with Retry-After; UI counts down. Unreadable addresses share one limit |
| Refresh within 30 s of the record's retrieval | Answered from the cache (`cached: true`, the record's own retrieval time); no provider request |
| Daily live-request budget spent (`LIVE_REQUESTS_PER_DAY`, 300 by default; every address together, per IST day) | Checks with a cached record are answered from the cache; the rest get 503 SOURCE_UNAVAILABLE, "Trakline has used today's live checks. Try again after 00:00 IST.", with Retry-After to midnight IST. No provider is asked. One `[budget]` warning a day, with the day and the limit only |
| Upstash slow or down | Cache misses; limits and the daily budget fall back to this instance's memory; checks keep answering |
| Provider failing repeatedly | 5 failures in 60 s open that caller's breaker for 30 s (doubling per failed probe, up to 10 min); the fallback answers at once and no request is spent on the failing provider. Live PNR checks and the availability crawler count separately, so one cannot rest the other |
| Provider refuses the key or plan, or its quota | Breaker open 10 min (401/403), or for the provider's Retry-After (429) — facts about the account, so these rest every caller of that provider |
| Sentry unreachable | Error reports are dropped; the app is unaffected |
| A script, style or connection the policy doesn't allow | Blocked by the enforced CSP; reported to Sentry from production; `tests/e2e/csp.spec.ts` fails on any violation on every route in both faces |
| Malformed API body | Client zod validation fails → error state, never rendered as data |
| Supabase unconfigured | Accounts surface says so; watchlist stays device-local; APIs 503 |
| Session expired | 401 → UI returns to local mode |
| Storage unavailable / corrupt | Stores degrade to empty; invalid records dropped on parse |
| Invalid or missing PNR after `/pnr#` | The check-again sheet; nothing is requested |

## State

- Device: `tt.watchlist.v2`, `tt.recent.v1`, `tt.theme`, `tt.install.v1`, `tt.mergePrompt.v1` — versioned keys, zod-validated on read, synced across tabs via `useSyncExternalStore`.
- Account: `watchlist_entries` with unique `(user_id, pnr)`; local→account merge is planned by `planMerge` and executed by `POST /api/watchlist/merge`.
- Shared (deployments only): Upstash Redis under `tt:{VERCEL_ENV}:`. The PNR cache is `pnr:v1:<HMAC>` → an AES-256-GCM value sealed to its key, 60 s. Limits are sliding windows keyed by an HMAC of the address (an IPv6 address by its /64) or user id. The daily live-request budget is a plain count per day in India, `budget:live:<date>`, kept two days, beside a marker that makes the day's `[budget]` warning fire once. The subkeys come from `DATA_KEY` (HKDF), so Upstash never holds a PNR, a record, an address or a user id in the clear. Any store failure is a cache miss, and the per-instance limiter. `upstash.ts` is the only module that imports Upstash.

## Testing

- `tests/unit` — pure logic and jsdom component tests (Vitest projects; `.test.ts` node, `.test.tsx` jsdom).
- `tests/unit/tokens.contract.test.ts` — the design-system guard: AA contrast for every text role on every surface in both faces, the design-locked steel pairing held at 3:1, parity with `brand-colors.ts`, the Industry vocabulary (no rounded corners, signal tones, or instrument tokens), banned arbitrary size classes, spacing rhythm, no raw hex, 500-line cap.
- `tests/unit/utils/cn.test.ts` — class merging keeps the custom type scale (`text-label`, `text-body`, …) beside colours.
- `tests/integration` — route handlers against an in-memory Supabase fake.
- `tests/e2e` — Playwright, desktop + mobile, fixture mode; `axe.spec.ts` scans every route in both faces, with the design-locked steel pairing as the only exemption.
- `tests/e2e/console-auth` — a second Playwright config (`playwright.console.config.ts`, port 4211, serial, one worker) that runs after the fixture suite, against a real local Supabase stack (`E2E=1`, so console email is captured in an in-memory outbox and read back through `/api/test-outbox`) and a real Chromium virtual security key over CDP. `npm run test:e2e:console` (`scripts/console-e2e.mjs`) reads the running stack's URL and keys from `supabase status -o env` and never writes them anywhere; `psql` against the local database resets the console between tests, and `globalTeardown` (`tests/e2e/console-auth/global-teardown.ts`) empties it once the run is over, however much of it ran. That last part is not housekeeping: `supabase test db` runs against the same database afterwards, and several pgTAP files make statements about the whole console — `console_team()`'s roster, the "at least one Owner" floor, `has_owner()`, the Security-email list — which one leftover member falsifies. It used to rest on `team.spec.ts` sorting last under `workers: 1`, so a single-spec run left the database dirty and produced fourteen failures across five untouched files. `CONSOLE_SHOTS=<dir>` makes the audit-log specs drop screenshots there; unset, they take none.
- `.github/workflows/ci.yml`: on every pull request into `main` and every push to `main`, `verify` runs types, lint, unit and integration tests and a production build, and `e2e` starts the local Supabase stack, runs `supabase test db`, the fixture Playwright suite, then the console suite above. No secrets; fixture mode plus the local stack's own well-known development keys. `audit.yml` runs `npm audit` on production dependencies weekly and when the dependency files change. `tests/unit/ci-workflows.contract.test.ts` holds the policy.
